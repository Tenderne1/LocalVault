# LocalVault 数据迁移与备份设计

## 为什么不能直接把 A 电脑的加密数据塞进 B 电脑

每个 Vault 都有独立随机 salt，并生成独立的数据加密密钥（DEK）。B 电脑自己的 Vault 有另一套 DEK，因此不能拿 B 的 DEK 直接解开 A 的导出数据。

## `.lvx` 可迁移加密数据

导出流程：

1. 用户选择导出文件位置。
2. LocalVault 要求再次输入当前 Vault 主密码。
3. 使用 Vault salt + Argon2id 从主密码派生 KEK。
4. 用 KEK 验证并解开当前 Vault 的 DEK。
5. 用 DEK 加密密码条目，并使用 AEAD 做完整性认证。
6. 将 salt、由主密码保护的 DEK、密文数据写入 `.lvx`。
7. 主密码本身不会写入文件。

导入流程：

1. B 电脑选择 `.lvx`。
2. 要求输入 A 电脑的 Vault 主密码。
3. 从文件中的 salt 派生源 KEK。
4. 用源 KEK 解开 DEK。
5. 用 DEK 验证并解密条目。
6. 只在本地内存中把解密后的条目交给当前 UI 做冲突选择；随后仍按当前 Vault 的加密保存流程写回 B 电脑。

这意味着：**拿到 `.lvx` 文件但不知道 A 电脑主密码的人，不能直接得到密码明文。** 但如果主密码很弱，攻击者仍可对导出文件进行离线猜测，所以主密码必须足够强。

## `.vault` 加密备份

`.vault` 是完整数据库快照，不是“条目导出”。它适合完整恢复原 Vault。恢复时必须验证备份里的 `wrapped_dek` 能否由输入的主密码正确解开；验证失败时不替换当前 Vault。

恢复成功后，现在提供两种方式：

- **替换当前 Vault**：用备份中的完整数据库替换当前 Vault。适合当前 Vault 已损坏、需要回到某个历史状态的场景；替换前会尽量保留 `.pre_restore.bak`。
- **合并到当前 Vault**：不删除当前 Vault 的新数据。备份中的条目如果已经存在于当前 Vault（按稳定条目 ID 判断）则保留当前版本；备份里当前 Vault 没有的条目会追加，并自动重新编号。备份中缺少的分类会一并加入。

合并不会覆盖当前 Vault 的 Recovery Code / 恢复设置，也不会把备份的旧数据库文件直接替换当前数据库。

## 安全边界

- 不提供明文 CSV 导出，避免把密码直接落盘。
- 不把主密码保存到配置文件、localStorage 或 `.lvx`。
- 导出文件被窃取时，安全性主要取决于源 Vault 主密码的抗离线猜测能力。
- 如果怀疑主密码已经泄露，应立即在可信设备上更换主密码并重新导出/迁移数据。

## Recovery 答案长度

Recovery Code 仍要求足够长度，但密保答案不再限制“至少 12 个字符”。答案现在只要求**不能为空**，可以使用中文、英文、数字或混合内容。此前如果使用 `chars().count()`，一个汉字本身也会计为 1 个字符；现在取消这个最低字符数限制后，不会再要求用户填写 12 个汉字。

建议答案不要使用生日、学校、住址等容易被猜到的信息，并优先依赖高熵 Recovery Code。
